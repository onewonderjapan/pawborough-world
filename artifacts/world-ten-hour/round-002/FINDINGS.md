工具：`tools/longrun_driver.mjs`（真实输入链驱动+分段原始证据）、`tools/longrun_report.mjs`（停顿/堆趋势/预算锁定分析）。
环境：headless Chrome + 系统 Chrome + **SwiftShader 软件渲染基线**（无GPU；所有帧间隔/帧率数字均为软件基线，不代表硬件表现）。

原始证据：本目录 `longrun/<场景>/`（segments/*.json 为逐帧原始gap对+逐样本资源/堆/轨迹，longrun.json 为事件与退出规则）。

## 驱动方法（诚实口径）

- **移动**：Playwright 键盘 KeyW/P（页面 window keydown 原链路）；**转向**：测试环境标注的合成
  `document.dispatchEvent(MouseEvent('mousemove',{movementX}))`——经页面自己的 mousemove 处理器
  （`movementX*0.0023`）作用于同一 aim 状态，与物理鼠标在指针锁下的数学完全一致。
  实测 CDP `Input.dispatchMouseEvent` 与 Playwright `mouse.move` 在无头指针锁下都**不产生** movementX，
  合成事件是唯一能让"真实处理器"转向的注入方式；与 round-1 error probe 的合成 blur 同类，仅存在于测试驱动。
- **模式操作**：P（键盘）、V（键盘退出取景）、`#btn-walk`（真实点击，需先展开默认折叠的审查工具面板）、
  失焦用合成 window blur（round-1 同款）、恢复用页面自己的 `#fatal-retry`。
- **从不**写控制器状态/位置；唯一真值来源是 `record().walking.capsuleFeet` 与 headingRad。
- **ready 门**：`ready && routeCheck` 双条件——启动期路线自检会**同步驱动主胶囊**跑完全程往返，
  未等它结束就开始走会与自检打架（冒烟实证：主线程 5.7s 停顿 + 胶囊被拖到半街）。
- **轨迹**：从实际出生点（=验证锚点 bridgeStart [124.6,27.65] = 主街 ms-220，与 route.json 契约核对一致）
  向西沿主街推进，A弄/B弄以"去而复返"支线插入，西端台阶脚"被0.17m台级挡住"按 routeCheck 同规则记为到达；
  之后沿返程腿向东。卡死(>8s)记 walkStall 异常并执行~180°转身脱困（真实玩家动作）。

## 搭建期实证发现

1. **record() 的 session.pose 是事件时刻快照**（pause/resume/endWalk 时更新），不是实时朝向；
   路线证据需要实时 aim → record() 增补 `walking.headingRad/pitchRad`（2行诊断字段，零行为改变，
   与 round-1 增补 load.sharedAssetSources 同类；src/fangbangMain.js 在允许修改窗口内）。
2. **行走出生点 ≠ 路线起点**：主街入口出生在 bridgeStart（ms-220），不是 mainStreet[0]（[232.5,47.6]）。
   最初轨迹从 ms[0] 反向引入，把胶囊180°转向横穿建筑，卡死在店面墙角（冒烟实证）——
   已改为从出生点最近街点起轨。**契约本身无损**（bridgeStart 即入口锚点）。
3. **`#btn-walk` 在默认折叠的审查工具面板内**（不在 header）：取景模式下需展开面板才可点；
   行走+指针锁时不可点（与 round-1 UP-B2 一致），V 是唯一退出路径。长测的 P/V 循环按玩家路径展开面板后真实点击。
4. **启动期主线程停顿基线**：routeCheck 同步自检产生 ~5.7s 最大帧间隔（含去程+返程物理扫描），
   启动段 p99 ~750–980ms；稳态段（行走）最大帧间隔 350–700ms——全部为 SwiftShader 软件基线。
5. 三分钟冒烟（mainAB，default）：27 航点 / 62.1m / 2次P暂停 / 2次V切换 / 2次失焦循环 / 0异常，
   post-gc() 堆 79.09MB 稳定，三角形 694430 精确锁定。

## 长跑结果

### S1：主街+A/B 全线（default，冷启动，35:00，`longrun/s1-mainAB-default-cold/`）

- **路线**：267/267 航点全命中（去程 ms-220→ms-334 台阶脚1.3m内、A/B弄去而复返、返程至出生点），
  实走 2,440m；9次P暂停、9次V取景往返、9次失焦清键循环，全部成功无异常。
- **稳定性**：42,732帧；帧间隔 p50=16.7ms（60fps满帧）、p99=583ms、max=5,733ms（仅启动期routeCheck）；
  除启动外 >1s 的停顿全程只有2次（4.3s在+13s启动段、1.4s在+732s）。SwiftShader 软件基线平均20.5fps。
- **资源**：三角形 694430 全程精确锁定；几何/材质/纹理 496/476/346 首尾一致（无泄漏迹象）。
- **堆**：显式gc()后平台 79.1→81.2MB，斜率 +3.75MB/h——35分钟不足以判定泄漏，
  列为后续更长跑（≥1h）的观察项；瞬时（gc前）峰值如实留档不作为泄漏证据。
- **真实缺陷（世界边界类，已留证待机主决定）**：轨迹完成后旧版驱动未松W（已修），胶囊东行越过
  bridgeStart，在 **x≈127–134, z≈22–28**（桥东街面末端）走出可行走面，坠入无限虚空——
  页面**没有任何坠落防护**（routeCheck 的 fallCheck 只存在于巡游自检，实况行走的 WalkSession 没有），
  直到35分钟跑结束胶囊仍在下落（y=-657,884m），无fatal、无复位、无提示。
  玩家沿街自然东行即可触发。修复建议（几何施工超本批范围）：WalkSession 加落地安全网
  （y<-0.5 复位到最后安全落点，同 routeCheck fallCheck 规则）或在街面末端加不可见边界。
  证据：`segments/seg-010.json`（坠落逐2s轨迹）+ 后续段连续坠落记录。

### S2：A弄+全配置（skins+props，冷启动，35:03，`longrun/s2-laneA-allon-cold/`）

- **路线**：339/97 航点（350%——6次失败恢复重载后从A弄出生点重开路线，重复圈为设计负载），
  实走 1,206m；6次P暂停、6次V往返、6次失焦循环、**6次注入资源失败→fatal→单次重试全部成功**，
  重载后均正确回到行走并就近重join轨迹，0异常。
- **资源**：三角形 708066（allOn预算）全程精确锁定；几何/材质/纹理 648/563/518 首尾一致。
- **堆**：post-gc() 81.3→82.7MB，斜率 +4.27MB/h——与 S1 的 +3.75MB/h 同量级，
  两次独立配置都出现 ~4MB/h 的缓慢爬升，列为主要长测观察项（是否GC堆 arena 增长待≥1h长跑判定）。
- **真实发现（软件基线性能）**：allOn 在 SwiftShader 下 **p50 帧间隔=500ms（≈2fps）**，
  而同机 default 配置 p50=16.7ms（60fps）——全配置的绘制调用数使软件渲染掉一个数量级。
  固定步进物理的 dt 钳制(0.25s)让行走呈半速"慢放"（2103s实走1206m≈0.57m/s）。
  这不构成代码缺陷（GPU机器不受此限），但对"低配机评审体验"是真实约束，如实留给机主。
- **报告口径注意**：每次重载后 rAF 时间戳归零，故跨重载的帧停顿 "at +Ns" 是**页相对时间**
  （4次 ~4.7s 停顿 = 4次重载后的启动自检+着色器编译，非运行中突然卡死）。

## 2026-09-21 附记（round-3 对上文的诚实修正，原文保留不改）

对照本轮 S4（同轨迹、加修复的驱动）与 S1 原始 `longrun.json`，上文的 S1 两处记载不准确：

1. **「267/267 航点全命中」应为 266/267**。S1 的 `exitRules.routeWaypointsHit=266`：旧驱动没有
   「轨迹完成即松 W」逻辑（2e8c084 才加入），走完 back-221 后继续东行越过 bridgeStart 坠落，
   back-220 从未命中。台账/FINDINGS 误写为 267/267。
2. **「实走 2,440m」混入了坠落期抖动**。同一轨迹的真实行走距离约 1.06km（S4 用修复后驱动完整
   走完、终点 back-220 命中，`metersWalked=1060`）；S1 计程器把坠落期 feet 每 2s 样本的水平抖动
   （x≈121–134、z≈11–26 间反复横跳）也累加进去了，多出的 ~1.38km 不是行走。
3. 路线坐标口径确认无误：route.json `mainStreet[220]=[124.6,27.65]` 即 bridgeStart，行走出生点
   两轮一致（ready 行的 feet=[230.9,47.65] 是巡游胶囊位置，非行走出生点）。
4. **「机器期间无其他重负载干扰」需要更正口径：负载主要来自我们自己的 SwiftShader 渲染进程**。
   round-3 用 `top` 实测：长测期间 chrome（SwiftShader）单进程占 ~1400% CPU（20 核机的 14 个核），
   其余进程均 <1 核。逐段 loadavg 10–17 与帧间隔的重/轻起伏是**软件光栅化的视图/阶段依赖成本**：
   出生点望穿整条主街的长视景、启动期管线编译等重帧阶段，SwiftShader 会并行铺满多核（loadavg 高、
   帧间隔 133–483ms）；中段近墙视角帧便宜（p50=16.7ms、loadavg 1.5–3.5）。因此「p50=16.7ms
   （60fps 满帧）」只在轻视图阶段成立，**不能作为全跑代表值**；S2/S3 的帧数字与 S1 各段一样是
   同一软件基线在不同视图/阶段下的真实成本，跨场景对比必须按段标注视图与阶段，不能只引用最优窗口。
   （本附记初版曾把这归因为「外部作业干扰」，经进程级实测证伪并在此更正。）

S4 本身结论（详见 round-003 FINDINGS）：62 分钟同轨迹全程干净完成；post-gc 堆 79.06→79.63MB，
斜率 **+0.46MB/h（前半 +0.89 / 后半 +0.18，趋平）**，round-2 的 ~4MB/h 缓升在 ≥1h 尺度未复现
为线性泄漏。帧时序按段保留了原始 gap 对与视图/阶段上下文；堆/资源/轨迹数据与渲染负载无关，
两者都完整可复核。
